1. Components: two product APIs, two mocks

Naming convention: services that ship end in Api. Fake external parties end in Mock or Simulator, are used only in development, and never ship.

Product:5001

InstagramSenderApi

Outbound. Sends messages and media to Instagram for many tenants without exceeding Meta's limits.

  • Bounded FIFO queue per tenant
  • Pre-flight gates: usage throttle, per-second pacing
  • Polly retry and circuit breaker, per tenant
  • Reads Meta's usage headers and error codes; persists blocks to SQL
Mock:5020

InstagramGraphMock

Plays Meta's Graph API (/v25.0/{tenant}/messages|media|media_publish).

  • Usage headers on every response
  • Rate-limit errors as HTTP 400 plus a code, like the real API
  • Named scenarios under /simulator/*
  • Replaced in production by graph.facebook.com through one config value
Product:5002

WebhookIngestApi

Inbound. The public webhook receiver, hardened against floods and abuse.

  • Fail-fast rule chain, cheapest check first
  • HMAC X-Hub-Signature-256 checked before any counter
  • Sliding-window limits: global, per-IP, per-client
  • Concurrency cap, bypass for GET and health paths, observe-only mode
Mock:5010

WebhookTrafficSimulator

Plays Instagram and attackers, firing traffic at the ingest API.

  • 8 scenarios: steady, burst, DDoS, global flood, oversized, bad signature, slow-loris, mixed
  • Returns status-code counts and observed rate-limit headers
  • In production, Meta itself calls the ingest API

2. What Meta limits, and how we see each limit

Meta enforces four independent scopes. Staying within one says nothing about the others, which is why one counter cannot model them.

The usage headers report percentages only. Meta's Instagram budget is 4800 x impressions per 24 h, so the absolute ceiling is never known. That is why the 80% threshold is the main defence, not a fixed calls-per-hour quota.

4. Inbound pipeline: WebhookIngestApi

The rules run in a fixed order (by the Order property, not by DI registration). The first denial ends the request, so cheap checks protect expensive ones and forged traffic never uses up a real client's quota.

Every 429 carries Retry-After, X-RateLimit-Limit, -Remaining and -Reset. The counters increment as each rule passes, so a request denied at a later rule has already used its earlier slots (this explains the 47 + 13 = 60 split in 3.1).

7. Algorithm map vs the textbook five

The textbook list (token bucket, leaky bucket, fixed window, sliding-window log, sliding-window counter) assumes you own the limit. On the outbound side Meta owns it, so about half our mechanisms are not on that list.

Not implemented, on purpose: the sliding-window counter and leaky-bucket strategies. Both are defensible for a single in-memory instance. When inbound moves to Redis across several instances, per-IP is where log memory grows with key count. The fix is a fourth strategy plus one config value, with no rule changes.
